## 核心判断

当前项目适合定位为**可审计的本地交易研究工具和人工条件计划工具**。已有较好的保守边界：没有实盘入口；历史数据证据不足拒绝正式模拟；持仓与订单有独立账本；前瞻观察没有伪装成 fills、净值或收益；新闻与社区缺失保留未知。主要短板已从“再加几个因子”转向**日期、规则版本、账户快照和失败恢复之间是否能保持一致**。

目前不能证明机械策略、新闻增强或任何其他策略赚钱。个人资产和持仓尚未录入，前瞻冻结样本为 0，首次实际定时采集和后续 D+1/D+5/D+20 都尚待验证。历史真实 PIT 档案与开盘成交证据尚未验收。这些是数据和实验的完成条件，不能由更多合成测试替代。

已独立复现的最重要问题是：基准缺行会悄悄改变 D+N；实验规则身份漏掉参数/新闻规则；旧规则的当日 planner 计划仍可显示非零数量；ST 名称会遮住本已触发的止损。另确认了当日选股失败会阻断旧样本观察的控制流。

### F01 — 独立的 session spine 仍未贯穿所有研究路径

**位置：** `current_screen.py:215` 的 `expected = benchmark.index[-251:]`；`forward_lab.py` 的 `_evaluate`；`data.py:433` 附近的 `validate_snapshot` 基准检查；`strategy.py:408` 的 `market_regime`。

**触发与证据：** 用现有 forward fixture 冻结 2026-09-10，一个完整基准的 D+5 到期日为 09-17、价差 3.7186%。只删除基准的 09-14、保留股票原始行情，再观察：结果仍为 `known`，到期日变成 09-18、价差变成 4.5226%。这不是“缺行情记未知”，而是观察定义被重写。另将 260 日合成 Snapshot 的 2025-12-31 基准行删除，`validate_snapshot` 仍返回 `tradable=True/errors=[]`，当天 `market_regime` 实际使用 12-30 数据输出 bear。

**影响：** 行情供应商漏行可以同时改变预热窗口、持有期、基准差值和市场状态；股票行情完整并不能挽救基准日期错误。历史 receipt 能绑定“收到的是这些行”，不自动证明基准应有的行全部存在。

**最小修法：** 历史路径先核验所需 benchmark 与 Snapshot calendar 的日期覆盖，并要求市场状态使用当天基准，否则 unknown/拒绝相关模拟。当前/forward 增加独立、只读、版本化交易日历；根据交易日历计算 D+1/D+5/D+20，再检验股票与基准在这些固定日期是否有数据。冻结 `calendar_version` 和到期日期；日历超出有效覆盖范围时 unknown，不猜。

无需 Tushare 的可行路径是保存沪深交易所年度休市公告和来源/发布时间/采集时间/哈希，生成并核验 2025–2026 session 表，覆盖当前 251 日预热和 D+20；调休周末仍按交易所休市。不能仅比较两个行情源的日期交集，也不能直接把某个第三方库当成认证真值。

**有意义验收：** 删除股票日、删除基准日、双方同时删除同一日，三种情况均不得改变原 entry/exit 日期；新增错误工作日也应报日历冲突。春节、国庆跨期和跨年覆盖到期要有固定反例。历史基准当日缺失不得继续报告昨日市场状态为今日状态。

### F02 — 当日名单失败会阻断旧批次已经到期的观察

**位置：** `daily_lab.py` 的 `run`，调用顺序为 `screen → fetch_context → freeze → watch_codes → observe`，整个链共享一个异常出口。

**触发：** 当天新浪目录分页失败或新名单不满足发布条件，而腾讯历史和旧批次观察所需报价仍可用。代码在 `screen` 失败后直接退出，旧批次 D+1/D+5/D+20 完全不观察。

**影响：** 新信号源故障人为制造旧实验缺测；如果长时间故障，最终还可能错过有限历史接口可恢复范围。新闻异常也不应决定已有价格观察能否推进。

**最小修法：** 软件检查和共同的时间/日历门禁保留；新信号采集冻结与旧批次观察分成独立阶段，分别记录状态和错误。一阶段失败后继续另一阶段已获授权、数据充分的工作，最终报告明确“今日未新增 / 旧批次已更新”。不能为了成功状态放松任何冻结门禁。

**有意义验收：** 前一天已有冻结样本，当天 `screen` blocked，但所需真实形态行情有效：无新增 batch，旧 batch 出现到期观察；反向的历史价格失败不应撤销已成功冻结的新信号。两个阶段都失败时仍保存独立错误和报告。父级已接收并开始实现此项。

### F03 — 实验规则身份漏掉参数和新闻生成规则

**位置：** 被审查版 `forward_lab.py` 的 `_rules_hash`、`freeze`；`current_screen.py` 的 `source_hash/parameters`；`context_feed.py:26` 起的词典及 `_sentiment`。

**证据：** 被审查版规则哈希只包含 forward 文件、常量版本和筛选 `source_hash`；后者只含 current_screen/current_data。内存反例中，同 source_hash、改变 `selection.parameters` 后跨日冻结，`rules_hash` 完全相同。新闻词典、证据覆盖阈值或来源解析变化也没有完整进入这个身份。

**影响：** batch_id 不同只能说明两天输入不同，不能说明两天是否属于同一规则实验；未来按规则汇总时可混入不同筛选/新闻条件，版本透明度失效。

**最小修法：** 保存可读 `experiment_manifest`，明确筛选源码/参数/范围、新闻处理源码及阈值、arm 定义、观察口径/日历版本；用该 manifest 的规范化哈希标识实验。行情内容、当天候选与每天真实时间应进入 input_hash，不能把每天都变的值放入实验身份导致无法积累同一实验。观察规则变更另有 evaluator 身份，旧批次只读保留。

**有意义验收：** 同规则不同日期 identity 不变；只改新闻词典、选股门槛、股票范围、arm 构造之一，identity 必变；失败重试不改第一次冻结事实；旧记录缺 manifest 时标 legacy，不补造当时版本。父级已接收并委托修复，最终测试由父级确认。

### F04 — planner 计划失效条件不完整

**位置：** `planner.py:175` 的 `PlanStore.state`；`review` 开始读取 profile/positions，末尾读取 `account_revision`；`webapp.py` 的 planner 写入单任务锁。

**证据：** 构造同日、账户 revision 相同、`source_hash='old-rules'` 的已发布计划，`state()` 返回 complete，entry quantity 仍为 100。现有 state 只检查账户修订和年龄，没有核对当前规则源码。网页 API version 常量只能处理某次接口升级，不能代表每次规则变化。

另一项是多入口边界：单个网页 Jobs 锁阻止同网页任务期间修改，但 CLI `planner-review` 或第二服务实例可与账户写入并行。review 使用开始时 profile/positions，结果却写入末尾最新 account_revision，可能把旧输入结果标成新修订结果。此并发场景为控制流审查，未做生产并发实测。

**最小修法：** 共用 `planner_rule_fingerprint()`；state 发现规则不符时沿用现有 stale 行为，数量清零并要求重新复核。review 开始读取并绑定 revision，发布事务提交前再次比对；变化则拒绝发布有效计划或重新计算。历史查看仍允许看到原数据，但显著标为历史。

**有意义验收：** 当日 source_hash 改变即失效；只改报告样式是否失效要事先定义；复核途中账户变更不能产生带新 revision 的旧数量；原计划记录不得被改写。此项不要求自动终止受执行策略限制的旧后台。

### F05 — ST 名称隐藏了价格退出触发

**位置：** `planner.py:294` 附近 `holding_review` 的 `if risk_name(name) ... elif last <= stop ...`。

**证据：** 现有 fixture 中持仓 100 股、stop=94、close=93：普通名字得到“止损触发”、sell_quantity=100。只把两个来源名字都改为 `*ST Demo`，得到“风险复核”、sell_quantity=0，输出不再告诉用户止损已经触发。止盈/到期也受同一优先级影响。

**影响：** 风险增加反而使明确的原计划触发在 UI 中消失。没有下单，因此不是已产生错误成交；但它会误导人工复核。

**最小修法：** 将价格/时间触发与风险提示、执行限制分开记录。已触发止损应继续显示，同时展示 ST、停牌、可卖数量等待核验条件；未知价格或公司行动仍不得产生乐观卖出结论。拟退出数量仍只表示下个可交易时段的人工条件计划。

**有意义验收：** 普通/ST 名称的相同价格应有相同 exit trigger；ST 风险标签不消失；T+1/缺价/复权缺失仍能限制可执行状态，不能因拆字段而变成允许真实成交。

### F06 — 手工账户快照缺完整性对账

**位置：** `planner.py:34` 的 Profile、`save_position`、`review` 的 exposure/gross_left/risk_left 计算，约 493 行。

**触发：** 账户总资产 10 万、现金 2 万，却未录入实际 8 万市值持仓；或用户只更新成交后股数但未更新资金。当前模型只核验 cash≤capital，不知道已录入持仓是否完整，也没有账户快照时点/其他资产/冻结现金解释。

**影响：** 单笔整手和共享预算公式本身可正确，但建在不完整账户上，仍可能低估已有总仓和风险。已有 `portfolio_known` 只看已录入持仓，空列表会被视为已知。

**最小修法：** 增加账户核对时点、持仓完整性声明、冻结资金/其他资产解释字段；收盘复核展示 capital 与现金+持仓市值的差额及容差。未解释差额或过期快照时新开仓 quantity=0，仍显示条件价格和已有持仓风险。必须区分可用现金与总现金，不能武断要求两者永远相等。

**有意义验收：** 资金缺失、漏持仓、冻结现金、非股票资产、更新一半快照分别有合理结果；只能在完整性和数值对账同时满足后分配新预算。无需读用户实际资金即可用合成账户验收。

### F07 — 历史真实 PIT 仍需要可执行的数据接入里程碑

**位置：** `hardening.py:95` 的 `audit_real_snapshot`、`make_spine/add_valuations`；`data.py` 的 `build_snapshot/_normalise_actions`；`ledger.py:326` 起的公司行动；`engine.py` 的退市持仓检查。

**现状判断：** 已实现 independent inventory/session receipts、L/D/P、明确全天停牌与缺行情区别、独立陈旧估值、公司行动完整性门禁和退市停止。这些保护应保留，不能为了“跑通真回测”放宽。当前缺口是没有经来源核对的真实短区间，包含退市、长期停牌、除权/分红以及晚到修订的完整证据链。

**最小下一步：** 先选一个很短、含上述事件的真实案例集，逐字段列 source/known_at/fetched_at/available_at、原始文档、规范化值和缺口；输出供应商能力矩阵，分清“今天重建”“当时归档”“无法采购/无法验证”。复杂换股/退市结算不支持时继续停止，另建人工 resolution 事件契约，不删除持仓。

**有意义验收：** 有独立原件可逐日逐事件核对；删证券、删停牌日、变更公司行为、加入晚到版本均被查出；现金红利到账、送转可卖日和退市最终处置能对账。未拿到材料就维持 research-only，不能以文件哈希相符作为真值认证。

### F08 — 开盘代理与可交易收益之间仍缺独立证据

**位置：** `execution.py:74` 的 opening evidence，`broker.py:112` 的 `_opening_risk`，`risk.py` 的预算与订单，`ledger.py` 的 fill/费用处理。

**现状判断：** T+1、整手/清仓零股、费用日期、最低佣金、预留资金、停牌/限价/跳空拒绝已经存在，不能说系统“没有成交风控”。但 opening_volume/opening_observed_at 不能单独证明开盘时行业/ST/限价状态、报价可见性、报单时刻与队列容量；日终字段可以在账本结算时被拿来约束开盘代理。当前文档也承认这一点。

**最小下一步：** 先为一小组证券保存真正的开盘时点状态和价格证据，再生成订单级验证表：冻结条件、观测时间、预期价格/容量、拒绝原因、允许的结果范围。没有开盘前有效证据继续 no fill。现阶段不必实现一个没有校准数据的复杂盘口模拟器。

**有意义验收：** 修改 D 日盘中/收盘状态不得改变原本只允许使用开盘信息的成交；跳空、涨跌停、部分成交、撤单和停牌分别能用原始记录解释。最终若要评价账户收益，再加入成交回报/费用核对；当前仅有价格观察不能跨越这一步。

### F09 — 永久未知样本需要终止重试状态，运行健康需独立展示

**位置：** `forward_lab.py` 的 `_batch_watch_codes/watch_codes/observe`；`current_data.py:204` 的有限 640 根 bar 请求；`daily_lab.py` 的 latest 报告和检查日志。

**触发：** 某一窗口发生不可支持的公司行动、永久缺失或退市，结果一直 unknown；watch_codes 对任何非 known 状态持续跟踪。超过内部 640 天时标 stale，但仍属于非 known，继续请求；历史接口又只返回有限 bar，不能保证永久恢复。

**影响：** 未知样本本身保留是正确的，但无限重试会逐月增加网络与运行成本；“没有新错误”也不等于今天应运行的任务已实际成功。超时异常目前还可能没有完整 checks.log。

**最小修法：** 保留分母并增加 `unknown_final/retry_after/resolution_required` 的运行状态；达到有证据的不可恢复边界后停止自动下载，允许显式材料导入触发新修订。记录应运行日期、最后成功冻结、最后成功观察、各阶段时长/错误及数据年龄；`check-only` 的成功不能覆盖数据健康含义。

**有意义验收：** 长期不可恢复样本仍出现在所有统计分母与原因列表中，但不永久占用 watch 请求；可恢复失败按上限重试；进程崩溃/睡眠错过日、测试超时、来源返回旧日数据均在报告可分辨。不得补造错过的前瞻信号。

### F10 — 四组对照可以诊断排序，尚不能证明策略更好

**位置：** `forward_lab.py` 的 `_arms/_metrics/summary`；`daily_lab.py` 的 observation_table；`context_feed.py` 的词典与 coverage。

**现状判断：** 四组都在机械 Top 20 子集中，60/120 动量本已参与共同过滤；因此它们检验的是这个条件集合里的排序差异。news_guard 用“无风险 flags”放行，缺新闻的股票仍可能留下；其含义是“未观察到词典命中”，不是“经充分新闻核查无风险”。当前 unknown 分母与 arm overlap 展示是有价值的保护。

**最小下一步：** 冻结可读的实验卡：假设、共同 universe、信号时间、对照定义、缺失处理、主要终点、最小实际差异、评估频率、停止/晋升条件和所有尝试次数。按冻结日做配对比较，保留相同可观察集合与 coverage 分层；20 日窗口重叠，不能把代码×日期×三个 horizon 当独立样本。后续统计应采用能处理相关性的时间分块方法，而不是看到 60 日就机械宣布显著。

**可证伪实验：** 在同一机械候选和相同已知新闻覆盖内，比较原排序与新闻风险守门；预先固定主要观察终点和未知阈值。另比较原权重与更简单的单动量排序，检验复杂度是否带来稳定改善。若 guard 不足 5 只，价格选择比较与投资组合比较必须分开；后者要定义空余资金和连续重叠仓位，不能把已知价格均值当资金收益。

**有意义验收：** 任意一次候选/规则变更能追到实验卡和新版本；数据不足允许结论“不确定”；统计程序用无优势模拟检验不会频繁选出虚假赢家。当前不建议加入 MACD/RSI/ML/RL 或每天改阈值。

### F11 — 哈希记录应补齐可恢复的源码和依赖版本

**位置：** `engine.py:29` 的 source_fingerprint、current/planner/forward 的源码哈希，根目录 Git 和 `requirements-lock.txt`，本地启动脚本。

**证据：** 本次 `git log -1` 返回 master 尚无 commit；`git status --short` 显示项目文件未跟踪。现有 hash 能检测代码变化，却不能从 hash 恢复运行时的源代码。依赖版本/解释器变化也未完整进入每份实验身份与复现材料。

**影响：** 数月后可能知道两批不同，却无法重建某批究竟运行了什么；旧后台运行代码与磁盘代码的版本差异也会妨碍验收。

**最小修法：** 在批准范围内建立一次可回退发布：跟踪源码/非敏感配置/测试/文档，或保存不可变源码包；运行 manifest 记录代码版本、Python、依赖锁哈希、规则 manifest 和有效日历版本。提供只读的运行中版本诊断和清楚的人工重启入口。不要在未知状态下自动终止进程或把凭据放入发布包。

**有意义验收：** 在新临时目录用一个旧版本的源码+锁文件可重新计算同一离线输入；hash 不同能解释原因；旧后台版本可以被识别；重启后用户数据不变。是否创建 Git 提交由父级结合用户授权处理，本审查不代为提交。

### F12 — 需要一份权威规则对照，避免三个工具被当成同一策略

**位置：** `docs/STRATEGY.md`、README、CURRENT_RESEARCH、CONTINUOUS_PLANS；`strategy.py`、`current_screen.py`、`planner.py`。

**证据与影响：** STRATEGY.md 仍写支持 SSE/SZSE/BSE 及 MAIN/CHINEXT/STAR/BSE，但共享规则已限定沪深 MAIN；其 ADV 描述仍写非停牌行均值，已与 session spine 修正冲突。历史 market_regime 为报告用 MA200+20 日斜率；planner 用 MA120 暂停新仓；当前筛选额外要求 60/120 动量均为正且 251 基准日都有成交。它们可以有不同目的，但不能把同名“机械基线”理解为一套完全相同规则。

**最小修法：** 建一张用途/股票池/历史证据/过滤/市场开关/持有与成交/资金口径表，给每条规则明确策略 ID；从同一 manifest 生成报告摘要，更新过期说明。设置清晰的完成状态：软件通过、数据就绪、信号冻结、观察到期、人工计划有效分别表示，不用一个“完成”覆盖所有含义。

**有意义验收：** 用户从任一报告都能确认它对应哪个策略、日期、输入范围和可执行程度；规格声明与当前默认配置一致；数据未知和账户未填时不会被误读为已推荐买入。首次真实采集及旧后台刷新后再进行界面验收。
